LISTA DE ERRORES ENCONTRADOS EN LA FASE DE TESTING
===============================================

Esta lista contiene todos los errores identificados durante la ejecución de tests, ordenados por importancia de resolución (de más crítico a menos crítico). Para cada error se incluye:
- Descripción del problema
- Impacto actual
- Importancia de solucionar (escala: Muy importante / Importante / Moderadamente importante / Menos importante)
- Dificultad de solucionar (escala: Fácil / Moderadamente fácil / Difícil / Muy difícil)

1. CONFLICTO ENTRE ASYNC Y SYNC EN EL BACKEND
   Descripción: El backend usa SQLAlchemy async (AsyncSession) pero los tests intentan usar sesiones síncronas, causando que los servicios no puedan acceder a la base de datos.
   Impacto: Todos los endpoints fallan con 500 Internal Server Error en tests.
   Importancia: Muy importante (impide que cualquier test funcione)
   Dificultad: Moderadamente fácil (requiere unificar async/sync o cambiar configuración de tests)

2. ERROR DE CONFIGURACIÓN DE BASE DE DATOS EN TESTS
   Descripción: Los fixtures de pytest retornan async_generator en lugar de sesiones de base de datos reales.
   Impacto: Tests de autenticación fallan porque no pueden ejecutar queries.
   Importancia: Muy importante (base de todos los tests)
   Dificultad: Moderadamente fácil (corregir configuración de fixtures)

3. PROBLEMAS DE HILOS CON SQLITE
   Descripción: SQLite in-memory no es thread-safe; TestClient ejecuta en hilos diferentes al que creó la DB.
   Impacto: Base de datos inaccesible desde tests, causando errores de tabla no encontrada.
   Importancia: Muy importante (impide ejecución de tests)
   Dificultad: Fácil (cambiar a SQLite basado en archivos con configuración thread-safe)

4. POSIBLE FALTA DE DATOS DE TEST
   Descripción: Tests de appointments asumen existencia de kinesiólogos (kinesiologo_id=1) sin datos de seed.
   Impacto: Tests de appointments fallarán si no hay datos iniciales.
   Importancia: Importante (afecta funcionalidad específica de appointments)
   Dificultad: Fácil (agregar fixtures para crear datos de test)

5. PROBLEMAS DE LIMPIEZA DE BASE DE DATOS DE TEST
   Descripción: Archivo de base de datos de test no se puede eliminar porque está siendo usado por otro proceso.
   Impacto: Tests no pueden limpiarse apropiadamente entre ejecuciones.
   Importancia: Moderadamente importante (inconveniente en desarrollo)
   Dificultad: Moderadamente fácil (mejorar manejo de cleanup en fixtures)

6. ✅ RESUELTO: WARNINGS DE DEPRECIÓN
   Descripción: Múltiples warnings sobre código deprecated en FastAPI y SQLAlchemy (on_event, declarative_base, etc.).
   Impacto: Código funciona pero eventualmente dejará de ser compatible.
   Importancia: Menos importante (no impide funcionamiento actual)
   Dificultad: Moderadamente fácil (actualizar dependencias y código)
   ✅ Solución aplicada: Actualizadas dependencias a versiones más recientes, reemplazado @app.on_event con lifespan handlers, actualizado declarative_base(), cambiado de python-jose a PyJWT, y de passlib[bcrypt] a passlib con pbkdf2_sha256.

=== ERRORES ENCONTRADOS EN TESTING MANUAL DEL FRONTEND ===

7. ✅ RESUELTO: PROTECCIÓN EXCESIVA DE RUTAS EN BOOKING
   Descripción: La página de reserva de turnos (/booking) requiere autenticación inmediata, impidiendo que usuarios no registrados vean kinesiólogos y horarios disponibles.
   Impacto: Usuarios no pueden explorar servicios sin registrarse primero, UX pobre.
   Importancia: Importante (afecta experiencia de usuario)
   Dificultad: Fácil (permitir vista pública de kinesiólogos, requerir login solo para confirmar reserva)
   ✅ Solución aplicada: 
       - Modificada página Booking.tsx para permitir acceso público
       - Carga de kinesiólogos y horarios disponibles sin autenticación
       - Autenticación requerida solo para confirmar reserva
       - Indicador visual de "Vista pública" en header
       - Mensaje informativo explicando que login solo es para confirmar
       - Estado de reserva pendiente guardado en localStorage para restaurar después del login
       - Rutas backend /kinesiologos-profiles y /available-slots modificadas para acceso público

8. ✅ RESUELTO: CONFIGURACIÓN INCORRECTA DE CORS
   Descripción: CORS configurado para puerto 5173 pero frontend corre en 5174. Backend permite localhost:5173 pero frontend usa 127.0.0.1:8000.
   Impacto: Todas las peticiones API fallan con error CORS, aplicación no funcional.
   Importancia: Muy importante (impide cualquier interacción con backend)
   Dificultad: Fácil (actualizar configuración de CORS y URLs)
   ✅ Solución aplicada: 
       - Extendidos orígenes permitidos en backend para 5173 y 5174
       - Se añadió soporte para localhost y 127.0.0.1 en ambos puertos

9. ✅ RESUELTO: INCONSISTENCIA EN URLs DE API
   Descripción: Frontend configurado para usar http://127.0.0.1:8000/api pero backend corre en http://0.0.0.0:8000.
   Impacto: Peticiones API fallan con "Network Error", aplicación no puede comunicarse con backend.
   Importancia: Muy importante (impide funcionalidad completa)
   Dificultad: Fácil (unificar URLs entre frontend y backend)
   ✅ Solución aplicada: 
       - API baseURL de frontend ahora usa import.meta.env.VITE_API_BASE_URL o proxy relativo '/api'
       - Esto elimina desajustes entre dominios y aprovecha proxy Vite en desarrollo

10. ✅ RESUELTO: WARNINGS DE REACT ROUTER
    Descripción: Warnings sobre flags futuros de React Router (v7_startTransition, v7_relativeSplatPath).
    Impacto: Warnings en consola, no afectan funcionalidad actual.
    Importancia: Menos importante (solo warnings)
    Dificultad: Fácil (actualizar configuración de React Router)
    ✅ Solución aplicada: Actualizada la dependencia react-router-dom a la versión 7.14.2 para eliminar los warnings de compatibilidad de React Router.

11. ✅ RESUELTO: FALTA DE PROTECCIÓN EN DASHBOARD
    Descripción: Página de dashboard (/dashboard) no requiere autenticación y permite acceso como "Guest".
    Impacto: Información sensible expuesta a usuarios no autenticados, vulnerabilidad de seguridad.
    Importancia: Muy importante (problema de seguridad crítico)
    Dificultad: Moderadamente fácil (agregar protección de rutas con autenticación)
    ✅ Solución aplicada: Implementado componente ProtectedRoute que verifica autenticación antes de permitir acceso a rutas protegidas.

12. ✅ RESUELTO: MANEJO INADECUADO DE ERRORES DE RED
    Descripción: Frontend muestra "Network Error" genérico cuando falla conexión con API, sin distinguir entre CORS, timeouts, o errores del servidor.
    Impacto: UX pobre, usuarios no entienden qué está pasando.
    Importancia: Moderadamente importante (afecta experiencia de usuario)
    Dificultad: Moderadamente fácil (mejorar manejo de errores en interceptores de Axios)
    ✅ Solución aplicada: 
       - Función getApiErrorMessage() que distingue entre:
         * Errores de red (CORS, conexión fallida, timeout)
         * Errores del servidor (5xx)
         * Errores de autenticación (401)
         * Errores de validación (4xx)
       - Interceptores mejorados en Axios que formatean errores
       - Visualización clara de errores en Agenda, Dashboard, Booking
       - Contexto de autenticación mejorado con manejo de errores
       - Mensajes específicos y accionables en español para cada tipo de error

13. ✅ RESUELTO: AUSENCIA GENERALIZADA DE PROTECCIÓN DE RUTAS
    Descripción: Múltiples páginas (/dashboard, /agenda) permiten acceso sin autenticación, mostrando datos como "Guest".
    Impacto: Vulnerabilidades de seguridad críticas, exposición de información sensible.
    Importancia: Crítica (problemas de seguridad graves)
    Dificultad: Moderadamente fácil (implementar guards de autenticación en rutas)
    ✅ Solución aplicada: 
       - Creado componente ProtectedRoute que verifica autenticación
       - Aplicado a rutas /dashboard y /agenda
       - Redirección automática al login para usuarios no autenticados
       - Redirección inteligente después del login a la página originalmente solicitada
       - Rutas del backend ya protegidas con autenticación requerida
